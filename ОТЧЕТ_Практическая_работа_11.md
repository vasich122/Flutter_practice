## 1. Описание выполненной работы

### 1.1 Анализ текущей архитектуры

**Оценка сложности приложения:**
- Количество экранов: 8 (авторизация, главный экран, профиль, заявления, академические данные, посещаемость, курсы, оценки)
- Источники данных: локальное хранилище (in-memory)
- Требования к тестируемости: средние
- Жизненный цикл: учебный проект с возможностью развития

**Вывод:** Приложение относится к категории **средней сложности**, что делает Clean Architecture оптимальным выбором.

### 1.2 Реализация базового распределения на слои

Создана трехслойная архитектура:

#### UI Layer (Слой пользовательского интерфейса)
- Расположение: `lib/features/`
- Ответственность: отображение данных и обработка пользовательских действий
- Компоненты: экраны, виджеты, BLoC/Cubit для управления состоянием UI

#### Domain Layer (Слой предметной области)
- Расположение: `lib/domain/`
- Ответственность: бизнес-логика, правила предметной области
- Компоненты: Use Cases, интерфейсы репозиториев

#### Data Layer (Слой данных)
- Расположение: `lib/data/`
- Ответственность: получение и хранение данных
- Компоненты: DataSources, DTO, Mappers, реализации репозиториев

### 1.3 Применение Clean Architecture

#### 1.3.1 Создание слоя Models (core/models)

Выделен независимый слой бизнес-моделей:

```
lib/core/models/
├── user_model.dart
├── grade_model.dart
├── application_model.dart
├── academic_info_model.dart
├── attendance_record_model.dart
```

**Преимущества:**
- Устранение циклических зависимостей
- Чистое управление зависимостями
- Повышение переиспользуемости моделей
- Инкапсуляция источников данных

**Пример модели:**
```dart
/// Бизнес-модель пользователя
class UserModel {
  final String id;
  final String login;
  final String fullName;
  final String group;
  final int course;
  final String status;
  
  // Методы и конструкторы
}
```

#### 1.3.2 Создание интерфейсов репозиториев (domain/repositories)

Созданы абстрактные интерфейсы, говорящие на языке предметной области:

```
lib/domain/repositories/

├── grade_repository.dart
├── application_repository.dart
├── academic_repository.dart
├── attendance_repository.dart
```

- Определяют контракт на языке бизнеса
- Позволяют легко менять реализации

### 1.4 Реализация Data Layer с DTO и Mappers

#### 1.4.1 Структура DataSources

Каждый DataSource инкапсулирует свою "зону ответственности":

```
lib/data/datasources/
├── user/
│   ├── user_dto.dart
│   ├── user_mapper.dart
│   └── user_local_data_source.dart
├── grade/
│   ├── grade_dto.dart
│   ├── grade_mapper.dart
│   └── grade_local_data_source.dart
└── ...
```

**Принцип инкапсуляции:**
- DTO и Mappers находятся внутри папки конкретного DataSource
- Другие части приложения не знают о существовании DTO
- Специфика работы с источником данных скрыта

**Пример DTO и Mapper:**
```dart
/// DTO для пользователя
class UserDto {
  final String id;
  final String login;
  // ... другие поля
  
  Map<String, dynamic> toJson() => {...};
  factory UserDto.fromJson(Map<String, dynamic> json) => ...;
}

/// Mapper для преобразования DTO в бизнес-модель
extension UserMapper on UserDto {
  UserModel toModel() {
    return UserModel(
      id: id,
      login: login,
      // ...
    );
  }
}
```

**Преимущества подхода:**
- Полная инкапсуляция специфики API/БД
- Отсутствие утечек абстракций
- Гибкость для разных источников данных
- Упрощение тестирования

### 1.5 Применение паттерна Repository

#### 1.5.1 Абстрактный интерфейс Repository

Интерфейсы определены в Domain Layer и говорят на языке бизнеса:

```dart
abstract class UserRepository {
  Future<UserModel> getCurrentUser();
  Future<void> updateUserStatus(String status);
}
```

#### 1.5.2 Реализация Repository

Реализации находятся в Data Layer и координируют источники данных:

```
lib/data/repositories/
├── user_repository_impl.dart
├── grade_repository_impl.dart
├── application_repository_impl.dart
├── academic_repository_impl.dart
├── attendance_repository_impl.dart
└── course_repository_impl.dart
```

**Пример реализации:**
```dart
class UserRepositoryImpl implements UserRepository {
  final UserLocalDataSource _localDataSource;

  UserRepositoryImpl(this._localDataSource);

  @override
  Future<UserModel> getCurrentUser() async {
    final dto = await _localDataSource.getCurrentUser();
    return dto.toModel(); // Преобразование через Mapper
  }
}
```

**Преимущества Repository Pattern:**
- Use Cases не знают о существовании разных источников данных
- Возможность координации нескольких источников (кэш, сеть, БД)
- Единая точка доступа к данным
- Упрощение бизнес-логики

### 1.6 Настройка Dependency Injection

Создан централизованный service locator для управления зависимостями:

```dart
// lib/shared/service_locator.dart
void setupLocator() {
  // Регистрация Data Sources
  locator.registerLazySingleton<UserLocalDataSource>(
    () => UserLocalDataSource(),
  );
  
  // Регистрация Repositories
  locator.registerLazySingleton<UserRepository>(
    () => UserRepositoryImpl(locator<UserLocalDataSource>()),
  );
  
  // Регистрация Use Cases
  locator.registerLazySingleton<GetUserUseCase>(
    () => GetUserUseCase(locator<UserRepository>()),
  );
}
```

**Инициализация в main.dart:**
```dart
void main() {
  setupLocator();
  runApp(const MyApp());
}
```

### 1.7 Рефакторинг UI слоя

Обновлен ProfileCubit для использования Use Cases:

```dart
class ProfileCubit extends Cubit<ProfileState> {
  final GetUserUseCase _getUserUseCase;
  final UpdateUserStatusUseCase _updateUserStatusUseCase;

  ProfileCubit({
    GetUserUseCase? getUserUseCase,
    UpdateUserStatusUseCase? updateUserStatusUseCase,
  })  : _getUserUseCase = getUserUseCase ?? locator<GetUserUseCase>(),
        _updateUserStatusUseCase =
            updateUserStatusUseCase ?? locator<UpdateUserStatusUseCase>(),
        super(const ProfileState(isLoading: true)) {
    loadUser();
  }

  Future<void> loadUser() async {
    emit(state.copyWith(isLoading: true, error: null));
    try {
      final user = await _getUserUseCase();
      emit(state.copyWith(user: user, isLoading: false));
    } catch (e) {
      emit(state.copyWith(error: e.toString(), isLoading: false));
    }
  }
}
```

DataSources инкапсулируют работу с конкретными источниками данных. Каждый DataSource содержит DTO, Mapper и сам источник данных.

##### 2.4.1.1 grade_dto.dart (lib/data/datasources/grade/grade_dto.dart)

**Назначение:** Data Transfer Object для оценки из локального источника данных.

**Функциональность:**

- Методы `toJson()` и `fromJson()` для сериализации/десериализации
- Инкапсулирован внутри DataSource, не используется напрямую другими слоями

**Ключевые поля:**
- `id` - уникальный идентификатор оценки
- `subject` - название предмета
- `grade` - числовое значение оценки

**Пример:**
```dart
final dto = GradeDto(
  id: 'g1',
  subject: 'Математический анализ',
  grade: 4.7,
);
```

##### 2.4.1.2 grade_mapper.dart (lib/data/datasources/grade/grade_mapper.dart)
**Назначение:** Mapper для преобразования DTO в бизнес-модель.

**Функциональность:**
- Extension на `GradeDto` с методом `toModel()`
- Преобразует `GradeDto` в `GradeModel`
- Инкапсулирован внутри DataSource, не используется напрямую другими слоями
- Обеспечивает преобразование данных из формата источника в бизнес-модель

**Пример использования:**
```dart
final dto = GradeDto(id: 'g1', subject: 'Математика', grade: 4.7);
final model = dto.toModel(); // Преобразование в GradeModel
```

##### 2.4.1.3 grade_local_data_source.dart (lib/data/datasources/grade/grade_local_data_source.dart)
**Назначение:** Локальный источник данных для оценок.

**Функциональность:**
- Хранит список оценок в памяти (in-memory хранилище)
- Хранит заметки к оценкам в словаре `_notes` (gradeId → note)
- Симулирует асинхронные операции через `Future.delayed()`
- В реальном приложении здесь будет работа с SharedPreferences, Hive, SQLite и т.д.

**Инициализация:**
- При создании инициализирует список из 5 предустановленных оценок
- Создает пустой словарь для заметок

**Ключевые методы:**
- `Future<List<GradeDto>> getGrades()` - получение всех оценок (возвращает список DTO)
  - Симулирует задержку 100ms для имитации асинхронной операции
  - Возвращает неизменяемый список оценок
- `Future<GradeDto?> getGradeById(String id)` - получение конкретной оценки по ID
  - Ищет оценку в списке по идентификатору
  - Возвращает `null`, если оценка не найдена
- `Future<void> saveNote(String gradeId, String note)` - сохранение заметки к оценке
  - Сохраняет заметку в словарь `_notes` с ключом `gradeId`
  - Симулирует асинхронную операцию
- `Future<String?> getNote(String gradeId)` - получение сохраненной заметки
  - Возвращает заметку из словаря `_notes` по ключу `gradeId`
  - Возвращает `null`, если заметка не найдена

**Особенности реализации:**
- Все методы асинхронные (возвращают `Future`)
- Использует `List.unmodifiable()` для защиты от изменений списка оценок
- Заметки хранятся отдельно от оценок в словаре `_notes`
- Предустановленные оценки: Математический анализ (4.7), Алгоритмы (4.9), Базы данных (4.6), Проектирование ПО (4.8), Машинное обучение (4.5)

#### 2.4.2 Реализация репозитория (lib/data/repositories/grade_repository_impl.dart)

##### 2.4.2.1 grade_repository_impl.dart (lib/data/repositories/grade_repository_impl.dart)
**Назначение:** Реализация интерфейса `GradeRepository`.

**Назначение:** Реализация интерфейса `GradeRepository` из Domain Layer.

**Функциональность:**
- Принимает `GradeLocalDataSource` в конструкторе через dependency injection
- Реализует все методы интерфейса `GradeRepository`
- Преобразует `GradeDto` в `GradeModel` через Mapper
- Координирует работу с источником данных
- Скрывает детали работы с DataSource от Domain Layer

**Ключевые методы:**
- `Future<List<GradeModel>> getGrades()` - получает список DTO из DataSource, преобразует каждый в Model через mapper
  - Вызывает `_localDataSource.getGrades()` для получения списка DTO
  - Использует `map((dto) => dto.toModel())` для преобразования каждого DTO в Model
  - Возвращает список бизнес-моделей `GradeModel`
- `Future<GradeModel?> getGradeById(String id)` - получает DTO по ID, преобразует в Model
  - Вызывает `_localDataSource.getGradeById(id)`
  - Если DTO найден, преобразует его в Model через `dto.toModel()`
  - Возвращает `null`, если оценка не найдена
- `Future<void> saveGradeNote(String gradeId, String note)` - делегирует сохранение заметки в DataSource
  - Вызывает `_localDataSource.saveNote(gradeId, note)`
  - Не выполняет преобразований, так как заметки хранятся как строки
- `Future<String?> getGradeNote(String gradeId)` - делегирует получение заметки из DataSource
  - Вызывает `_localDataSource.getNote(gradeId)`
  - Возвращает строку заметки или `null`

**Особенности реализации:**
- Использует метод `map()` для преобразования списка DTO в список Models
- Все преобразования выполняются через Mapper extension (`dto.toModel()`)
- Repository не знает о деталях хранения данных, только координирует работу
- Реализует интерфейс `GradeRepository`, определенный в Domain Layer

### 2.5 Регистрация зависимостей (lib/shared/service_locator.dart)

**Назначение:** Централизованное управление зависимостями для функциональности оценок.

**Регистрация компонентов для оценок:**
1. **GradeLocalDataSource** - регистрируется как LazySingleton (создается при первом обращении)
2. **GradeRepository** - регистрируется с зависимостью от `GradeLocalDataSource`
3. **GetGradesUseCase** - регистрируется с зависимостью от `GradeRepository`
4. **SaveGradeNoteUseCase** - регистрируется с зависимостью от `GradeRepository`

**Пример регистрации:**
```dart
// Регистрация DataSource
locator.registerLazySingleton<GradeLocalDataSource>(
  () => GradeLocalDataSource(),
);

// Регистрация Repository
locator.registerLazySingleton<GradeRepository>(
  () => GradeRepositoryImpl(locator<GradeLocalDataSource>()),
);

// Регистрация Use Cases
locator.registerLazySingleton<GetGradesUseCase>(
  () => GetGradesUseCase(locator<GradeRepository>()),
);

locator.registerLazySingleton<SaveGradeNoteUseCase>(
  () => SaveGradeNoteUseCase(locator<GradeRepository>()),
);
```

**Инициализация:**
- Функция `setupLocator()` вызывается в `main()` перед запуском приложения
- Все зависимости регистрируются как LazySingletons (создаются при первом обращении)

**Использование в коде:**
```dart
// Получение Use Case через Service Locator
final getGradesUseCase = locator<GetGradesUseCase>();
final grades = await getGradesUseCase();
```

## 5. Выводы

### 5.1 Достигнутые результаты

1. **Разделение ответственности:**
   - UI Layer отвечает только за отображение
   - Domain Layer содержит чистую бизнес-логику
   - Data Layer инкапсулирует работу с данными

2. **Независимость Domain Layer:**
   - Domain Layer не зависит от Flutter, баз данных или сетевых библиотек
   - Может быть протестирован как обычная Dart-библиотека
   - Легко переносится на другие платформы

3. **Гибкость архитектуры:**
   - Легко добавить новые источники данных (API, БД)
   - Можно менять реализации без изменения бизнес-логики
   - Упрощено добавление новых функций

4. **Тестируемость:**
   - Use Cases легко тестируются с моками репозиториев
   - DataSources можно тестировать изолированно
   - Модели не требуют внешних зависимостей

5. **Масштабируемость:**
   - Четкая структура упрощает работу команды
   - Каждый разработчик может работать над своим слоем
   - Легко добавлять новые фичи

### 5.2 Преимущества Clean Architecture

1. **Изоляция бизнес-логики:**
   - Бизнес-правила не зависят от деталей реализации
   - Изменения в UI или Data не влияют на Domain

2. **Инверсия зависимостей:**
   - Domain определяет интерфейсы
   - Data реализует эти интерфейсы
   - Направление зависимостей строго внутрь

3. **Инкапсуляция:**
   - DTO и Mappers скрыты внутри DataSources
   - Специфика источников данных не просачивается наружу

4. **Repository Pattern:**
   - Единая точка доступа к данным
   - Возможность координации нескольких источников
   - Упрощение бизнес-логики

### 5.3 Применимость к проекту

Clean Architecture идеально подходит для данного проекта, так как:

- **Средняя сложность:** Проект имеет достаточное количество экранов и функций для оправдания архитектурных инвестиций
- **Потенциал развития:** Архитектура позволяет легко добавлять новые функции
- **Командная работа:** Четкое разделение слоев упрощает параллельную разработку
- **Тестируемость:** Структура способствует написанию unit-тестов
